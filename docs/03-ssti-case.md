# ৩. কেস স্টাডি: Server-Side Template Injection (/ssti/lab)

> PyGoat-এর `/ssti/lab` রুটে Django SSTI ভালনারেবিলিটি বিশ্লেষণ, এক্সপ্লয়েটেশন ও ফিক্স।

## SSTI ভালনারেবিলিটি বিশ্লেষণ (introduction/views.py)

**১. দুর্বল কোড বিশ্লেষণ (The Vulnerability)** introduction/views.py ফাইলে
দুটি ফাংশন খেয়াল করুন:

```python
def filter_blog(blog):
    # ডেভেলপার ফিল্টার ফাংশন বানিয়ে রেখেছে, কিন্তু ভেতরে কিছুই লেখেনি!
    pass

# ssti_lab এর ভেতরে:
blog = request.POST.get('blog')
filter_blog(blog)  # অকার্যকর গার্ড!

# ইউজারের ইনপুট সরাসরি .html টেমপ্লেট ফাইল হিসেবে ডিস্কে লেখা হচ্ছে (Sink!):
f.write(str_data)
return render(request, file_name)
```

**২. কোডের ৩টি জাদুকরী প্রশ্ন (The 3 Core Questions):** গত ক্লাসে আমরা যে
৩টি প্রশ্ন শিখেছিলাম, এখানে সেগুলো মিলিয়ে দেখি:

-   **Source (ইনপুট কোথা থেকে আসছে?):**
    > request.POST.get('blog')---অর্থাৎ ইউজার ফর্মের 'blog' বক্সে যা
    > লিখছে, সেটিই হলো ইনপুট।

-   **Sink (কোথায় গিয়ে কাজ করছে?):** ইউজারের লেখাটি সরাসরি একটি .html
    > ফাইল হিসেবে সেভ হয়ে ড্যাঙ্গোর render() ফাংশনের মাধ্যমে সার্ভারে
    > এক্সিকিউট হচ্ছে।

-   **Guard (মাঝখানে কেউ পাহারা দিচ্ছে কি?):** এখানে ডেভেলপার
    > filter_blog() নামে একটি পাহারাদার (Guard) বানিয়েছে, কিন্তু ফাংশনটির
    > ভেতরে শুধু pass লেখা! এর মানে হলো দারোয়ান আছে, কিন্তু সে গভীর ঘুমে
    > আচ্ছন্ন---সে ইনপুটটি নিরাপদ কি না তা যাচাই করছে না।

**৩. লাইভ এক্সপ্লয়েট বা হ্যাক করা (The Attack)** ব্রাউজারে /ssti/lab পেজে
গিয়ে ব্লগ বক্সে যদি সাধারণ কিছু না লিখে নিচের ড্যাঙ্গো টেমপ্লেট কোড (Payload)
লিখে সাবমিট করেন:

```django
{{ request.user.is_superuser }} {{ 7|add:7 }}
```

![Screenshot](images/image22.png)

**ফলাফল কী হবে?** সাবমিট করার পর ভিউ পেজে গেলে আপনি দেখতে পাবেন স্ক্রিনে
লেখা উঠেছে False 14 (অথবা আপনি অ্যাডমিন হলে True
14)।![](images/image6.png)

**এর মানে কী?** এর মানে হলো সার্ভার আপনার ইনপুটকে সাধারণ টেক্সট হিসেবে
দেখায়নি। ড্যাঙ্গো টেমপ্লেট ইঞ্জিন আপনার লেখা {{ 7|add:7 }} কোডটিকে সত্যি
সত্যিই প্রসেস করে ৭ আর ৭ যোগ করে ১৪ বানিয়েছে! একেই বলা হয় **Server-Side
Template Injection (SSTI)**। হ্যাকার চাইলে এই ফাঁক গলে ক্ষতিকর পাইথন কোড
চালিয়ে সার্ভারের ফুল কন্ট্রোল নিয়ে নিতে পারে।

### **কেন এই অ্যাটাকটি কাজ করে?**

**Sink (কোথায় কাজ করছে?):** কোডের সবচেয়ে মারাত্মক অংশ হলো blog =
prepend_code + blog + "{% endblock %}"। এখানে ইউজারের ইনপুটকে সরাসরি
ড্যাঙ্গোর র-টেমপ্লেট সিনট্যাক্সের সাথে জোড়া লাগানো হয়েছে। এরপর
file.write(blog) ব্যবহার করে সেই পুরো কোডটিকে সার্ভারের ডিস্কে একটি নতুন
{id}.html ফাইল হিসেবে সেভ করা হয়েছে।

**HTML কীভাবে রেন্ডার হচ্ছে এবং হ্যাক হচ্ছে?** সবশেষে return
redirect(f'blog/{id}') কল করা হয়েছে। যখন ইউজার ওই আইডির লিংকে
রিডাইরেক্ট হয়, তখন ড্যাঙ্গোর ডিফল্ট টেমপ্লেট ইঞ্জিন সার্ভারে সদ্য সেভ হওয়া ওই
{id}.html ফাইলটি রেন্ডার (Render) করে।

যেহেতু ইউজারের লেখা ইনপুটটি ভেরিয়েবল বা সাধারণ টেক্সট হিসেবে পাস না হয়ে
সরাসরি .html ফাইলের ভেতরে টেমপ্লেট কোড হিসেবে হার্ডকোড হয়ে সেভ হয়েছে, তাই
ইউজার যদি ইনপুটে {{ 7|add:7 }} লেখে, ড্যাঙ্গো টেমপ্লেট ইঞ্জিন ফাইলটি রেন্ডার
করার সময় সেটিকে পাইথন কোড হিসেবে এক্সিকিউট করে স্ক্রিনে ১৪ প্রিন্ট করে দেয়।
ড্যাঙ্গোর টেমপ্লেট ইঞ্জিনে এই অনিরাপদ এক্সিকিউশনকেই Server-Side Template
Injection বা SSTI বলে।

### **অ্যাডমিন পাসওয়ার্ড হ্যাশ বের করার ধাপ (The Exploit)**

SSTI-এর মাধ্যমে ডেটাবেস থেকে অ্যাডমিনের পাসওয়ার্ডের হ্যাশ বের করতে হলে
আমাদের এমন একটি অবজেক্ট খুঁজে বের করতে হবে যা থেকে ইউজারের ডেটাবেস রেকর্ডে
যাওয়া যায়। ড্যাঙ্গোর টেমপ্লেটে প্রায়ই request অবজেক্টটি গ্লোবাল কন্টেক্সট হিসেবে
থাকে। আমরা request.user ব্যবহার করে অ্যাটাক শুরু করব।

**ধাপ ১: সাধারণ SSTI চেক করা**

প্রথমে নিশ্চিত হতে হবে যে SSTI সত্যিই কাজ করছে কি না। ইনপুট বক্সে (যেমন আপনার
ল্যাবের /ssti/lab বা ব্লগের ঘরে) নিচের পে-লোডটি দিন:

```django
{{ 7|add:7 }}
```

**ফলাফল:** যদি এটি কাজ করে তবে আউটপুটে 14 দেখাবে। এর মানে সার্ভার আমাদের কোড এক্সিকিউট করছে।

**ধাপ ২: বর্তমান ইউজারের তথ্য দেখা**

এবার বর্তমান ইউজারের তথ্য চেক করতে নিচের পে-লোডটি দিন:

```django
{{ request.user }}
```

**ফলাফল:** এটি দিলে স্ক্রিনে আপনার বর্তমান ইউজারনেম প্রিন্ট হবে।

**ধাপ ৩: পাসওয়ার্ডের ঘরে পৌঁছানো (The Data Leak)**

ড্যাঙ্গোর User মডেলে ইউজারের পাসওয়ার্ড একটি এনক্রিপ্টেড হ্যাশ হিসেবে password
অ্যাট্রিবিউটে সংরক্ষিত থাকে। যেহেতু আমরা ইনপুটকে ফিল্টার ছাড়াই রেন্ডার করাতে
পারছি, আমরা সরাসরি বর্তমান ইউজারের পাসওয়ার্ড হ্যাশটি কল করতে পারি:

```django
{{ request.user.password }}
```

pbkdf2_sha256$260000$...) প্রিন্ট হয়ে যাবে।

### **এই অ্যাটাক থেকে বাঁচার উপায় (The Fix)**

আপনার কোর্স ম্যাটেরিয়াল এবং ভিডিওগুলোতে যেমন শেখানো হয়েছে, এই দুর্বলতা ফিক্স
করার জন্য যা করতে হবে: ১. ইউজারের ইনপুট দিয়ে কখনোই নতুন .html টেমপ্লেট ফাইল
তৈরি করে সার্ভারে রেন্ডার করানো যাবে না। ২. ড্যাঙ্গোর ডিফল্ট টেমপ্লেটে
ভেরিয়েবল পাস করলে তা অটোমেটিকভাবে এস্কেপ (Auto-escape) হয়ে যায়, কিন্তু
ডেভেলপার যদি ভুল করে mark_safe বা |safe ব্যবহার করেন, তবে সেটি বাদ দিতে
হবে। ৩. ইনপুট স্যানিটাইজ করার জন্য একটি প্রপার ভ্যালিডেশন বা গার্ড (Guard)
ফাংশন ব্যবহার করতে হবে।
